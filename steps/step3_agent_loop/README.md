## 先记住两条核心认知就够了

1. **`messages` 列表就是 agent 的全部记忆与状态。**
   harness 里所有花哨概念（上下文管理、压缩、记忆），本质都是在管理这张列表。
2. **模型从不执行任何东西，它只输出"我想执行 X"。**
   真正的执行永远发生在你自己的 Python 进程里 ——
   所以"权限 / 沙箱 / 审批"这些 harness 概念才会存在。

## 到时候你会看到什么

`agent_loop.py` 只比 step1 的裸调用多三样东西：

1. 一个工具 `run_bash` —— agent 的"手"
2. `create()` 多传一个 `tools=` 参数 —— 告诉模型它有手可用
3. 一个循环 —— 模型要工具 → 执行 → 结果塞回 `messages` → 再问模型，
   直到给出最终回答

```
用户提问
   │
   ▼
┌─────────────────────────────┐
│  messages ──► 模型          │
│                │            │
│      要调工具？─┴─ 是 ──► 执行工具
│                │            │ │
│                否            │ └─ 结果追加进 messages（回到顶部）
│                ▼            │
│            最终回答          │
└─────────────────────────────┘
```

伪代码：

```text
while True:
    回复 = 模型(全部历史消息 messages)
    if 回复.要求调用工具:
        结果 = 执行工具(回复.工具调用)
        把结果追加进 messages        # 喂回给模型
    else:
        return 回复.内容             # 最终回答
```

循环只有两个出口：模型不再要工具（完成），或触发 `max_turns`（保险丝）——
这个保险丝是最早出现的 harness 安全机制。

## 和 step2 的呼应

step2 的流式循环：模型持续给你**文字流**，你逐段处理。
step3 的 agent 循环：模型持续给你**要做的事**（工具调用），你逐件执行、把结果喂回去。

理解了"循环 + 喂回"，agent loop 就只剩语法细节了。
